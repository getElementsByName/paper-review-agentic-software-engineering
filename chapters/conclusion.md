
# 역할 전환: 10배 개발자에서 100배 협업자 담론으로

<KeyMessage message="생산성 차이는 코드 타자량이 아니라 협업 설계 능력에서 나온다." />

- 차별화 포인트 변화
  - 과거: 타이핑 속도, 개인 구현력
  - 현재: 브리핑 품질, 컨텍스트 통제, 검증 설계
- 인간 역할: 구현자 + 지휘자
- (100x/1000x 는 보편 실증치보다 상징적 표현)

<SourceNote text="§1, §7.7 + 프로젝트 핵심 메시지" />

# 교육과 역할 전환

<KeyMessage message="인간 책임은 상향 이동한다; 교육도 프롬프트 팁에서 설계·검증·거버넌스 중심으로 재편해야 한다." />

- 개발자 역량 재정의
  - 명세 설계, 시스템 사고, 정책 설계, 증거 해석
- 역할 이동
  - 코더 중심 → 코치/오케스트레이터 중심

# 개발자 업무의 본질

<KeyMessage message="소프트웨어 공학은 끝까지 인간 영역이며, 무엇이 에이전트로 넘어가고 무엇이 인간에게 남는지 구분이 핵심이다." />

- **인간도 툴 호출** — 모호하거나 인간 결정이 필요한 지점에서 LLM이 휴먼 툴을 잘 호출할 수 있는가?
- **프로젝트 명세** — 컨텍스트 엔지니어링 영역에서 에이전트가 내재화한 부분과 인간이 결정해야 하는 영역 구분
- **본질: 소프트웨어 공학** — LLM·에이전트·생태계가 담당하는 영역과 구분했을 때, 소프트웨어 공학은 끝까지 인간의 영역이며 개발자 업무의 본질

# 토론 질문과 쟁점 언어

<KeyMessage message="찬반 토론에서 반복 사용할 수 있는 질문 언어를 확보한다." />

- **속도 vs 신뢰**: 우리 팀에서 생성 속도와 검증/리뷰 비용의 균형을 어떻게 측정하고 조정할 것인가?
- **MRP 도입**: 테스트 통과만으로 머지하는 기준을 언제, 어떤 단계부터 증거 묶음 기준으로 바꿀 것인가?
- **브리핑 품질**: BriefingScript 또는 계획 품질을 정량·정성적으로 어떻게 평가할 것인가?
- **리뷰 병목**: 병렬 생성 대비 직렬 리뷰 병목을 완화하기 위해 계획/근거 선검토를 어디서부터 도입할 수 있는가?
- **협업 구조 전환**: 1:1 에이전틱 코딩에서 N:N 에이전틱 소프트웨어 엔지니어링으로 옮기기 위해 가장 먼저 바꿀 행위자·프로세스·산출물은 무엇인가?

# 결론: 속도는 기술, 신뢰는 구조

<KeyMessage message="신뢰는 구조화된 협업·명시적 기준·버전 관리된 의사결정에서 만들어진다; 키워드와 쟁점 질문으로 다음 탐색을 이어간다." />

- 에이전틱 소프트웨어 엔지니어링의 본질은 코드 생성 자체가 아니라 협업 구조
- SASE는 공통 언어와 개념 프레임을 제공
- 실무 핵심 전환
  - 도구 팁 중심 → 개념어 중심
  - 즉답 중심 → 쟁점 정의 중심

<SourceNote text="§9" />
