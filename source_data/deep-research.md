발표 스토리라인 및 스크립트
1. 서론: LLM의 환상과 차가운 현실
• 슬라이드 1: LLM은 시스템이 아니라 '함수'다
    ◦ 내용: LLM은 상태를 저장하는 지능이 아니라 stateless한 요청-응답 함수에 가깝습니다. API 수준에서 모든 요청은 독립적이며, 대화의 상태는 모델이 아니라 개발자가 관리해야 하는 영역입니다. 또한 LLM은 기본적으로 다음 토큰 예측(NTP) 기반으로 작동하므로, 명시적인 탐색이나 검증 루프 없이는 장기적인 계획을 일관되게 유지하기 어렵습니다.
    ◦ 스크립트: "많은 이들이 AI가 모든 것을 기억하고 스스로 계획한다고 믿지만, 기술적으로 LLM은 매 호출마다 상태를 새로 구성해야 하는 stateless 함수입니다. 우리는 모델 자체의 지능에 의존할 것이 아니라, 상태와 검증 루프를 어떻게 설계할 것인가에 집중해야 합니다."
• 슬라이드 2: 프롬프트만으로 넘을 수 없는 '80%의 벽'
    ◦ 내용: temperature가 0이어도 LLM의 출력은 완전한 결정성을 보장할 수 없습니다. 특히 RLHF(인간 피드백을 통한 강화 학습)는 모델을 '도움이 되는 톤'으로 최적화하지만, 이 과정에서 **언어적 과신(Overconfidence)**을 유발하여 모르는 것도 아는 척하는 '도움 편향(Helpfulness bias)'을 만듭니다. 결과적으로 초기 80%의 성과는 빠르지만, 나머지 20%의 신뢰성을 확보하는 검증 단계가 전체 비용을 지배하게 됩니다.
    ◦ 스크립트: "단순히 프롬프트를 잘 쓰는 것만으로는 시스템의 신뢰성을 70~80% 이상 올리기 어렵습니다. 특히 RLHF는 모델을 단정적으로 말하게 만들어 과신을 유발할 수 있으므로, 생성된 결과에 대한 별도의 검증과 보정이 반드시 필요합니다."
2. 본론 (1): 프롬프트를 넘어 컨텍스트 엔지니어링으로
• 슬라이드 3: 에이전트 설계를 위한 12가지 원칙 (12-Factor Agents)
    ◦ 내용: 프로덕션 에이전트는 단순히 모델을 호출하는 프로그램이 아니라 소프트웨어 관점에서 설계되어야 합니다. 핵심은 컨텍스트 윈도우를 소유하고 관제하는 것입니다. 멀티에이전트 구성 시에는 모든 작업에 에이전트를 늘리기보다, 과제의 성격에 따라 **계획(Planner)-실행(Worker)-검증(Judge)**의 역할을 분리하는 것이 효과적입니다.
    ◦ 스크립트: "'12-Factor Agents' 원칙에 따라 에이전트의 관제 포인트를 모델이 아닌 컨텍스트와 상태 구성으로 옮겨야 합니다. 무조건 에이전트 수를 늘리는 것이 답이 아니며, 과업의 특성에 따라 역할을 구조적으로 분리해야 성능 저하를 막을 수 있습니다."
• 슬라이드 4: 컨텍스트 관리 전략: Write, Select, Compress, Isolate
    ◦ 내용: 컨텍스트가 길어질수록 모델의 성능이 비선형적으로 흔들리는 '컨텍스트 부패(Context Rot)' 현상이 발생합니다. 이를 해결하기 위해 필요한 정보만 선택(Select)하거나, 요약(Compress)하고, 중요 정보를 격리(Isolate)하는 엔지니어링 전략이 필수적입니다. 또한, RPI(Research-Plan-Implement) 워크플로우를 통해 읽기, 계획, 쓰기 단계를 분리하면 환각 비용을 크게 줄일 수 있습니다.
    ◦ 스크립트: "입력 길이가 늘어날수록 모델의 이해력은 비균일하게 떨어집니다. 따라서 우리는 Write/Select/Compress/Isolate라는 4가지 전략을 통해 컨텍스트를 엄격히 관리하고, 생각과 실행을 분리하는 RPI 패턴을 도입해야 합니다."
3. 본론 (2): SASE - 에이전틱 소프트웨어 엔지니어링의 미래
• 슬라이드 5: SE 3.0의 비전, SASE(Structured Agentic Software Engineering)
    ◦ 내용: SASE는 에이전트 협업을 프로세스와 아티팩트 단위로 재설계하는 프레임워크입니다. 인간이 의도와 승인에 집중하는 **ACE(Agent Command Environment)**와 에이전트가 병렬로 작업을 수행하는 **AEE(Agent Execution Environment)**라는 두 가지 워크벤치를 분리할 것을 제안합니다. (보안 용어인 SASE와 혼동 주의 필요)
    ◦ 스크립트: "이제는 IDE 중심의 개발을 넘어 인간과 에이전트의 협업 환경을 분리하는 SASE 비전으로 나아가야 합니다. 사람은 전략과 감사에 집중하고, 에이전트는 구조화된 환경에서 실행을 담당하는 구조입니다."
• 슬라이드 6: 속도(생성)보다 신뢰(검증)에 집중하라
    ◦ 내용: DORA 리서치에 따르면 AI 도입은 개인의 타이핑 속도를 올리지만, 조직 전체의 스루풋(-1.5%)과 안정성(-7.2%)에는 오히려 부정적 신호를 줄 수도 있습니다. 숙련된 개발자일수록 AI 결과물을 검증하고 수정하는 데 더 많은 시간을 쓰기 때문입니다. 따라서 단순한 PR 대신, 검증 근거를 포함한 증거 번들(MRP, Merge-Readiness Pack) 중심의 리뷰로 전환해야 합니다.
    ◦ 스크립트: "AI는 코드를 빨리 만들지만, 검증은 자동으로 이루어지지 않습니다. 대량 생성 시대의 리뷰는 코드를 읽는 것이 아니라 '증거'를 읽는 것이어야 하며, 이를 위해 구조화된 증거 패키지인 MRP 도입이 시급합니다."
4. 본론 (3): 운영 모델과 팀의 변화
• 슬라이드 7: 코드로서의 멘토링(Mentorship-as-Code)
    ◦ 내용: 팀의 규범과 정책을 일회성 코멘트로 남기지 말고 MentorScript와 같은 코드로 승격시켜 에이전트가 학습하고 준수하게 만들어야 합니다. 또한 **MCP(Model Context Protocol)**와 같은 표준 인터페이스를 통해 도구 연결을 표준화하면 운영의 복잡성을 낮출 수 있습니다.
    ◦ 스크립트: "팀의 노하우를 **'코드로서의 멘토링'**으로 구조화하십시오. 에이전트가 팀의 정책을 자동으로 준수하게 함으로써 반복되는 리뷰 부하를 줄일 수 있습니다."
• 슬라이드 8: AI를 도구가 아닌 '동료'로 대하라
    ◦ 내용: 인간은 전략가이자 심판의 역할을 맡아야 합니다. AI에게 단순히 지시만 내리는 것이 아니라, **"어떻게 하면 나를 도울 수 있는지 질문하라(Reverse Prompting)"**는 규범을 통해 요구사항의 누락을 방지하고 맥락 정보를 풍부하게 수집할 수 있습니다.
    ◦ 스크립트: "AI를 단순한 검색창이 아니라 맥락을 질문하는 주니어 동료처럼 대하십시오. **역프롬프팅(Reverse prompting)**을 팀 규범으로 채택하는 것만으로도 협업의 질이 달라집니다."
5. 결론: 단계적 도입과 로드맵
• 슬라이드 9: 확장 전략: 병렬 탐색과 N-version 검증
    ◦ 내용: 병렬 에이전트를 활용해 탐색의 폭을 넓히고, 동일한 과업을 여러 방식으로 구현한 뒤 판정(Judge)하는 N-version 프로그래밍을 통해 신뢰를 확보할 수 있습니다. 최종 머지는 항상 구조화된 증거(MRP)를 기반으로 이루어져야 합니다.
    ◦ 스크립트: "고위험 작업에는 여러 후보를 병렬로 생성하고 테스트로 검증하는 구조를 도입하십시오. 확장의 핵심은 에이전트의 수가 아니라 품질 게이트와 책임 추적 체계에 있습니다."
• 슬라이드 10: 성공적인 도입을 위한 로드맵
    ◦ 내용: 기술 PoC에 머물지 말고, 파일럿 → 확장(CI/MRP 강화) → 거버넌스(정책 코드화) 단계로 접근해야 합니다. 조직의 변화 관리는 기술 도입과 동시에 이루어져야 합니다.
    ◦ 스크립트: "에이전트 도입은 단순한 툴 도입이 아니라 운영 모델의 변화입니다. 명확한 지표를 가지고 단계적으로 확장하여, AI와 인간이 공존하는 새로운 엔지니어링 표준을 만들어 가길 바랍니다."
발표 스토리를 계획하고 발표 스크립트를 작성하라

제공해주신 '컨텍스트 엔지니어링 및 에이전트 소프트웨어 엔지니어링' 리서치 자료를 바탕으로, 에이전트 시대의 새로운 소프트웨어 공학 패러다임에 관한 발표 스토리 라인과 상세 스크립트를 구성해 드립니다.

[발표 스토리 구성안]
1. 도입: LLM의 민낯 - 상태 없는 함수
    ◦ LLM은 지능형 시스템이 아니라 '요청-응답' 함수라는 점을 강조하며 기존의 오해를 교정합니다.
2. 전개 1: 생성의 속도와 신뢰의 격차
    ◦ AI 도입이 개인의 코딩 속도는 올리지만, 왜 조직 전체의 생산성(DORA 지표)은 오히려 떨어질 수 있는지 병목 지점을 진단합니다.
3. 전개 2: 프롬프트를 넘어 '컨텍스트 엔지니어링'으로
    ◦ 단순한 질문(Prompt)을 넘어 모델의 작업 메모리인 컨텍스트를 설계하고 관리하는 구체적 전략을 제시합니다.
4. 핵심: SASE - 구조화된 에이전트 소프트웨어 공학
    ◦ 에이전트 협업을 위한 새로운 프레임워크(SASE)와 이를 지탱하는 아티팩트(MRP, CRP 등)를 소개합니다.
5. 결론: 인간의 새로운 역할 - 에이전트 코치
    ◦ 타이핑하는 개발자에서 전략을 수립하고 증거를 감사하는 '전략가/심판'으로의 역할 변화를 제언합니다.

[발표 상세 스크립트]
Slide 1. LLM은 '상태'가 없습니다: 신뢰성은 루프에서 나옵니다
여러분은 LLM이 우리와 대화하며 모든 것을 기억한다고 생각하시나요? 사실 **LLM은 "상태를 내장한 시스템"이 아니라 단일 호출에 응답하는 "Stateless 함수"**에 가깝습니다. API 관점에서 각 요청은 독립적이며, 대화의 상태는 오직 개발자가 구성하는 컨텍스트를 통해서만 유지됩니다. 따라서 에이전트의 신뢰성은 모델 자체의 성능이 아니라, 매 호출에 공급되는 컨텍스트, 상태 관리, 그리고 검증 루프를 어떻게 설계하느냐에 달려 있습니다.
Slide 2. 왜 AI를 도입했는데 릴리스는 더 느려질까요?
AI가 코드를 빨리 생성함에도 불구하고, 조직 차원에서는 '딜리버리 안정성'이나 '스루풋 저하'라는 리스크 신호가 보고되고 있습니다. DORA 2024 보고서에 따르면 AI 도입은 개인 생산성에는 긍정적이지만, 조직 성과(안정성 -7.2%)는 오히려 떨어뜨릴 수 있다는 상충 신호가 나타납니다. 숙련된 개발자일수록 AI가 만든 코드를 검증하고 수정하는 비용 때문에 작업 시간이 역으로 늘어나기도 합니다. 우리는 이제 '생성 속도'가 아니라 '검증과 통합'의 병목에 주목해야 합니다.
Slide 3. '컨텍스트 로트(Context Rot)'와 엔지니어링 전략
프롬프트를 잘 쓰는 것만으로는 한계가 명확합니다. 입력 길이가 늘어날수록 모델의 성능이 비선형적으로 흔들리는 '컨텍스트 로트' 현상이 발생하기 때문입니다. 이를 해결하기 위해 단순한 프롬프트 작성을 넘어선 컨텍스트 엔지니어링이 필요합니다. 구체적으로는 컨텍스트를 외부에 저장하는 Write, 필요한 정보만 뽑는 Select, 양을 줄이는 Compress, 그리고 서브태스크를 분리하는 Isolate 전략을 통해 모델의 작업 메모리를 최적화해야 합니다.
Slide 4. SASE: 에이전트 시대를 위한 소프트웨어 공학 3.0
이제 에이전트 협업을 위해 **SASE(Structured Agentic Software Engineering)**라는 새로운 비전이 필요합니다. SASE는 인간이 지휘와 감사를 담당하는 **ACE(Agent Command Environment)**와 에이전트가 실제 작업을 수행하는 **AEE(Agent Execution Environment)**로 워크벤치를 분리할 것을 제안합니다. 또한, 일회성 대화 대신 BriefingScript나 MentorScript처럼 버전 관리가 가능한 구조화된 아티팩트를 통해 에이전트의 동작을 제어해야 합니다.
Slide 5. '코드 읽기'에서 '증거 감사'로: MRP의 도입
대량의 코드가 생성되는 시대에 인간이 모든 라인을 읽는 것은 불가능합니다. 그래서 우리는 **MRP(Merge-Readiness Pack)**라는 '증거 번들'에 주목해야 합니다. 머지 여부를 결정할 때 코드를 하나하나 읽는 대신, 에이전트가 제출한 테스트 결과, 정적 분석, 설계 근거 등의 증거를 감사하는 방식으로 리뷰 프로세스를 재설계해야 합니다. 이것이 바로 생성의 속도를 검증의 신뢰로 연결하는 핵심 장치입니다.
Slide 6. 마무하며: AI를 팀원으로 대하십시오
결국 인간의 역할은 '코드 타이퍼'에서 **'전략가, 멘토, 그리고 심판'**으로 이동하고 있습니다. AI를 단순한 도구로 쓰기보다, "어떻게 하면 나를 더 잘 도울 수 있니?"라고 질문하게 만드는 주니어 동료처럼 대하십시오. 기술적 PoC를 넘어, 역할과 책임, 증거 기반의 승인 모델을 포함한 운영 모델의 변화가 동반될 때 비로소 에이전트 기반 소프트웨어 공학은 완성될 것입니다.
